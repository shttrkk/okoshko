# Чек-лист требований (Definition of Done)

Построчная выжимка из `CASE.md` и `RULES.md`. Каждый пункт — проверяемый критерий приёмки.
Статус ведётся в `docs/STATUS.md` репозитория: `[ ]` не начато, `[~]` в работе, `[x]` сделано и проверено (с указанием, как проверено).

## A. Суть кейса

| ID | Требование (источник) | Критерий приёмки |
|---|---|---|
| A1 | Прототип агентной системы, которая собирает уникальные характеристики отелей **и номеров** (CASE: Формулировка) | Характеристики есть на уровне отеля И на уровне номера/фасада/этажа (например вид — по сторонам и этажам) |
| A2 | Источники — открытые данные (OSM, карты высот, публичные датасеты и API) **и отельеры** | Минимум 6 разных открытых источников реально использованы в данных демо; у каждого значения указан источник |
| A3 | Систематизировать, хранить и показывать пользователю | Есть хранилище с единым форматом значений и UI, где пользователь видит значения |
| A4 | Список отелей, данные, инструменты агентов, логику, интерфейс собираем сами | Скрипт сбора списка отелей региона из открытых данных лежит в репо и воспроизводим |
| A5 | «Агент, который просит LLM угадать — не решение». Нужно знать: откуда агент берёт значение, насколько уверен, как проверить, когда устареет | У каждого значения: source, method, evidence (ссылка/артефакт расчёта), confidence, observed_at, valid_until; ни одно значение не появляется из «LLM угадал» без пометки и низкой уверенности |
| A6 | Один регион, проработанный глубоко | Все демо-данные — один регион; 100+ отелей с полным набором характеристик |
| A7 | Запуск по README без многочасовой загрузки; демо-данные заранее собраны и лежат в репо | `docker compose up --build` поднимает всё с уже посчитанными данными; пересчёт — отдельная опциональная команда |
| A8 | Если нужен ключ LLM — описать в README и приложить `.env.example` | Есть; без ключа демо всё равно работает (fallback/кэш), это написано в README |

## B. Основные задачи (обязательные)

| ID | Требование | Критерий приёмки |
|---|---|---|
| B1 | **Сбор характеристик**: агент сам решает, какие источники и инструменты нужны для конкретной характеристики, и получает значение | Есть реестр инструментов; агент-планировщик строит план по описанию характеристики; в UI/логах виден трейс: какие инструменты выбраны и почему |
| B1.1 | Хотя бы одна характеристика вычисляется по геоданным, а не находится в тексте | Минимум: вид на море/закат по фасадам и этажам (DEM + высоты зданий + LOS + положение солнца) + шум по сторонам здания + реальная пешая доступность с перепадом высот |
| B2 | **Диалог с отельером**: если данных не хватает, агент задаёт вопрос, принимает ответ в свободной форме и раскладывает по полям; отельера можно имитировать | Вопросы генерируются автоматически по пробелам/низкой уверенности; есть имитатор отельера; свободный ответ превращается в структурированные поля с валидацией; виден весь цикл в UI |
| B3 | **Хранение и достоверность**: у каждого значения есть источник, уверенность и дата получения | Схема БД это гарантирует (NOT NULL); UI показывает источник, уверенность и дату у каждого значения |
| B3.1 | Если источники противоречат друг другу, система это замечает и разбирается | Детектор конфликтов + стратегия разрешения (веса источников, перепроверка, вопрос отельеру); в демо есть минимум 3 реальных конфликта, показанных в UI с объяснением решения |
| B4 | **Расширяемость**: новую характеристику можно добавить без переписывания системы, например описав её текстом | Новая характеристика добавляется файлом-описанием (YAML/MD) или формой в UI; агент сам подбирает инструменты и считает её; в демо показано добавление новой характеристики вживую |
| B5 | **Поиск по запросу**: пользователь своими словами описывает, что ему важно («тихий номер с видом на закат недалеко от моря»), получает подходящие отели | NL-запрос разбирается в жёсткие и мягкие условия (видны и редактируются как чипы); выдача ранжирована; работает на русском; набор из 20+ тестовых запросов проходит |

## C. Дополнительные задачи

| ID | Требование | Критерий приёмки |
|---|---|---|
| C1 | **Объяснение выбора**: почему подходит и в чём не дотягивает («вид на закат есть, но только с 5-го этажа») | У каждого результата блок «подходит / не дотягивает / неизвестно» с привязкой к условиям запроса и к источникам |
| C2 | **Сравнение** нескольких отелей или номеров по собранным характеристикам | Экран сравнения 2–4 отелей/номеров с подсветкой лучшего значения и уверенности |
| C3 | **Кабинет отельера**: видит, что система узнала; подтверждает/исправляет; отвечает на вопросы агента | Отдельный раздел с тестовым входом; подтверждение/правка меняет значение и его источник/уверенность; ответы на вопросы проходят через парсер |
| C4 | **Актуализация**: повторная проверка устаревших данных; реакция на изменения (рядом построили дом — закрыли вид) | Планировщик перепроверки по valid_until; сценарий «новое здание» (симуляция изменения OSM/DSM) пересчитывает вид и показывает было/стало |
| C5 | **Метрики качества**: своя размеченная выборка; точность характеристик, покрытие, доля вопросов к отельеру | Размеченный датасет в репо (с методикой разметки), скрипт подсчёта метрик, страница/отчёт с цифрами |

## D. User stories (проверка смысла)

| ID | Кто | Что должно быть видно в демо |
|---|---|---|
| D1 | Путешественник: быстро найти отель, чтобы на месте всё оказалось так, как хотел | Путь «запрос → выдача с объяснениями → карточка с доказательствами» укладывается в секунды |
| D2 | Островок: знать больше, чем в карточках → точнее подбор, рост конверсии, меньше отмен | Дашборд: сколько новых характеристик, покрытие, уверенность; аргументация в README/презентации |
| D3 | Отельер: сильные стороны видны нужным гостям; отвечать на вопрос один раз | Кабинет показывает, по каким запросам отель находится; ответ отельера переиспользуется для всех гостей |
