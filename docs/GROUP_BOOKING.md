# Несколько гостей, номера и даты

Текущий поиск проверяет, могут ли разные пожелания выполняться в одном отеле в разных положениях номера. «Запад, этажи 7–9» — срез геометрии и фактов, а не товар из каталога и не обещание свободного номера. Два запроса могут выбрать одинаковый срез. Число доступных номеров, кровати, вместимость, цены и соседство в текущих открытых данных отсутствуют.

## Данные для подключения номерного фонда

Авторизованный адаптер каталога и наличия платформы, PMS или channel manager должен передавать:

| Данные | Назначение |
|---|---|
| Стабильные hotel_id, room_type_id и, где доступно, room_id | Сопоставить поставщика с отелем и фактическим номером |
| Тип, кровати, основные и дополнительные места, возрастные ограничения | Проверить вместимость и совместимость гостей |
| Количество номеров по типу, стороне и этажу | Отличить два независимых запроса от двух доступных номеров |
| Календарь наличия по ночам, ограничения заезда и длительности | Проверить разные даты и непрерывность проживания |
| Тариф, валюта, налоги, сборы, питание и условия отмены | Рассчитать полную стоимость предложения |
| Этаж, коридор, расстояние, смежные двери и подтверждённая смежность | Проверить требование «рядом» |
| Квартиры, спальни, общая вместимость и правила совместного проживания | Рассмотреть размещение вне гостиничного номерного фонда |
| Время наблюдения, срок действия, источник и версия предложения | Повторно проверить предложение перед бронированием |

Доступность должна подтверждаться поставщиком атомарно при удержании или бронировании. Статический остаток не гарантирует продажу. Если есть только остаток по типу, можно предложить тип, но нельзя обещать конкретные окна, этаж или соседство без подтверждённого распределения. Для интеграции нужны договорный доступ и согласование идентификаторов; прототип сейчас не обращается к API платформ бронирования.

## Задача назначения «гость → номер → ночь»

Пусть `x[g,r,t]` означает размещение гостя `g` в номере `r` в ночь `t`; `y[r,t]` — использование номера. Активные ночи гостя задаются полуинтервалом `[заезд, выезд)`. Каждый активный гость получает ровно одно место на ночь. Вне своих дат назначения нет.

Жёсткие ограничения:

- Доступность номера на каждую занятую ночь; суммарная вместимость и допустимый состав гостей.
- Совместимость кроватей, возрастов и обязательных пожеланий каждого человека.
- Совместное размещение указанных пар и разделение тех, кому нужен отдельный номер.
- Достоверно подтверждённые сторона, этаж, доступность маршрута и правила для питомцев.
- Если соседство обязательно, оно проверяется только при наличии данных о фактических номерах.

Переезд — смена `r` между последовательными активными ночами одного гостя. Его можно запретить либо включить со штрафом. Разные даты заезда не требуют переселения остальных, если назначение остаётся допустимым. Неизвестное обязательное свойство не считается выполненным.

Целевая функция минимизирует взвешенную сумму полной стоимости, расстояний между номерами компании, числа переездов и неудовлетворённых пожеланий. Цена сравнивается в согласованной валюте за весь период; расстояние — только по известным этажам и планировкам. Веса выбирает пользователь. Мягкие пожелания не могут компенсировать нарушение жёстких условий. Если решения нет, система показывает минимальный конфликт условий и предлагает явное ослабление; изменение не применяется молча.

Для реального номерного фонда подходит целочисленная модель или CP-SAT. При доступности только по типам сначала решается агрегированная задача с остатками, а конкретное распределение остаётся за поставщиком. Этот раздел описывает будущий решатель: в прототипе его нет.

## Два примера

**Семья из пяти человек.** Сначала уточняются возраст, совместное размещение, кровати и кто из двух гостей хочет одноместное размещение. «Одноместный тип» и «один человек в двухместном номере» различаются тарифом и доступностью. Бабушкино ограничение по этажу и маршруту проверяется отдельно; общее пожелание жить в одном отеле — совместно. Текущий прототип уже разделяет такие пожелания, но не утверждает, что пять человек поместятся в выбранных номерах.

**Компания из тридцати человек.** Люди объединяются только в явно заданные пары или подгруппы. Для каждого задаются даты и обязательные условия, для компании — бюджет и важность соседства. Решатель резервирует нужное число мест по ночам, учитывает разные даты, считает стоимость и штрафы за разнесение или переезд. При отсутствии планировки слово «рядом» остаётся неподтверждённым. Прототип не принимает тридцать раздельных запросов: HTTP-контракт ограничен двенадцатью запросами положений, паспорт — тридцатью пунктами.

## Связь с текущими компонентами

`ParsedQuery.rooms` хранит пожелания отдельных людей или номеров; общие `must/nice` проверяются один раз. `RoomScope` задаёт сторону, диапазон этажей и месяц. Сопоставление независимо выбирает совместимое положение для каждого запроса, не расходуя выдуманный остаток.

`RoomProfile` описывает положение шаблонами по свежим фактам. Каждая утвердительная фраза содержит `fact_ids`; спорное, неизвестное и синтетическое подписаны. Эти профили можно сопоставить с номерным фондом после появления связки `room_id → scope`.

Паспорт ожиданий сохраняет подпись и индекс запроса, пожелания и доказательства; один ответ отеля проверяет пункты отдельно по номерам. Подтверждение свойств не является удержанием или оплатой. Вопрос отелю передаёт требуемый scope, но сам по себе не создаёт факт о существующем номере. Новые ответы проходят разбор, цитаты и явное подтверждение, после чего обновляются факты и зависимые представления.

Прототип сознательно не рассчитывает цену, не продаёт размещение на даты, не обещает смежные номера, не назначает кровати и не строит чат с выдуманным каталогом. Следующий этап требует реального инвентаря и транзакционного контракта поставщика.
