## 1. Агентные фреймворки для Python (2026) и MCP

### Takeaway
Для хакатона лучше всего подходит **тонкий собственный оркестратор**: детерминированный пайплайн и state machine в Python с таблицами трейсов в Postgres. Вызовы LLM внутри него делаются через **PydanticAI** (типизированный вывод с тремя режимами tool/native/prompted, любой OpenAI-совместимый `base_url`) или через голый `openai` SDK с Pydantic-валидацией. Есть две альтернативы. OpenAI Agents SDK даёт лучший tracing «из коробки», но по умолчанию работает через Responses API и шлёт трейсы в OpenAI. LangGraph даёт durable HITL-граф, но порог входа у него выше. smolagents (исполняет сгенерированный LLM код) и CrewAI (тяжёлые ролевые абстракции) для истории про «достоверность» подходят хуже. MCP можно добавить опционально, чтобы показать открытость реестра инструментов, но внутренний агент от него зависеть не должен.

### Cited Findings
- Актуальные версии на 2026-10-26: `openai-agents` 0.24.0 (2026-10-15), `pydantic-ai` 2.61.0 (2026-10-24), `langgraph` 1.2.17 (2026-10-24), `smolagents` 1.26.0 (последний релиз 2026-05-29, то есть выходит реже остальных), `crewai` 1.15.30 (2026-10-24), `openai` 3.37.0, `litellm` 1.106.4, `instructor` 1.17.0, `mcp` 2.3.0, `fastmcp` 4.1.4 — [PyPI openai-agents](https://pypi.org/project/openai-agents/), [PyPI pydantic-ai](https://pypi.org/project/pydantic-ai/), [PyPI langgraph](https://pypi.org/project/langgraph/), [PyPI smolagents](https://pypi.org/project/smolagents/), [PyPI crewai](https://pypi.org/project/crewai/), [PyPI mcp](https://pypi.org/project/mcp/), [PyPI fastmcp](https://pypi.org/project/fastmcp/)
- **OpenAI Agents SDK, сторонние провайдеры.** Есть три способа подключения: `set_default_openai_client(AsyncOpenAI(base_url=..., api_key=...))` глобально, `ModelProvider` на один `Runner.run` и `Agent.model` на конкретного агента. Можно также передать `OpenAIChatCompletionsModel(model=..., openai_client=client)`. Адаптеры LiteLLM (`openai-agents[litellm]`) и Any-LLM помечены как beta / best-effort — [OpenAI Agents SDK: Models](https://openai.github.io/openai-agents-python/models/)
- **OpenAI Agents SDK, Responses API.** SDK по умолчанию использует **Responses API**, которого у многих провайдеров нет, поэтому возможны 404. Документация советует вызвать `set_default_openai_api("chat_completions")` или взять `OpenAIChatCompletionsModel`. Поля, которые есть только в Responses (`previous_response_id`), в Chat Completions молча отбрасываются. Чтобы падать сразу, нужен `strict_feature_validation=True`. Для провайдеров, которые нестабильно стримят tool-call deltas, есть `buffer_streamed_tool_calls=True` — [OpenAI Agents SDK: Models](https://openai.github.io/openai-agents-python/models/)
- **OpenAI Agents SDK, structured output.** Часть провайдеров поддерживает только JSON mode без JSON schema и отвечает ошибкой вида `'response_format.type' : value is not one of the allowed values ['text','json_object']`. Без поддержки схемы возможен битый JSON — [OpenAI Agents SDK: Models](https://openai.github.io/openai-agents-python/models/)
- **OpenAI Agents SDK, tracing.** Трейсы по умолчанию загружаются в OpenAI. Без ключа OpenAI появляется `Tracing client error 401`. Варианты: `set_tracing_disabled(True)`, `set_tracing_export_api_key(...)` или собственный trace processor — [OpenAI Agents SDK: Models](https://openai.github.io/openai-agents-python/models/). Обзор v0.24.0 подтверждает, что tracing включён по умолчанию и уходит в дашборд OpenAI — [Geekflare](https://geekflare.com/open-source/openai-agents-sdk/) (в обзоре дата 19.10.2026, на PyPI загрузка 15.10.2026, расхождение несущественное).
- **OpenAI Agents SDK, процессоры и спаны.** `add_trace_processor()` добавляет процессор, при этом экспорт в OpenAI сохраняется. `set_trace_processors()` заменяет процессоры по умолчанию. Типы спанов: `agent_span`, `generation_span`, `function_span`, `guardrail_span`, `handoff_span`, `task_span`, `turn_span`, кастомные через `custom_span()`. Список интеграций включает Arize Phoenix, Pydantic Logfire, Langfuse, MLflow, LangSmith, Opik и другие — [OpenAI Agents SDK: Tracing](https://openai.github.io/openai-agents-python/tracing/)
- LiteLLM документирует экспорт спанов Agents SDK через OpenInference и предупреждает, что успешный вызов модели не гарантирует успешного экспорта трейса — [LiteLLM: openai agents](https://docs.litellm.ai/docs/proxy/lens/integrations/openai-agents)
- **PydanticAI, подключение моделей.** `OpenAIChatModel` работает через Chat Completions, `OpenAIResponsesModel` используется по умолчанию для префикса `openai:`. Endpoint настраивается через `OpenAIProvider(api_key=...)` или `OpenAIProvider(openai_client=AsyncOpenAI(base_url=...))`. У клиента по умолчанию `max_retries=2` — [PydanticAI: OpenAI](https://pydantic.dev/docs/ai/models/openai/)
- **PydanticAI, режимы вывода.** Есть три режима structured output: `'tool'` (по умолчанию), `'native'` (`NativeOutput`, нативный response_format, опция strict) и `'prompted'` (`PromptedOutput`, схема вставляется в промпт через плейсхолдер `{schema}`) — [PydanticAI output API](https://pydantic.dev/docs/ai/api/pydantic-ai/output/), [PydanticAI profiles](https://pydantic.dev/docs/ai/api/pydantic-ai/profiles/). Пользователь сообщает, что `NativeOutput` работает против OpenAI-совместимого endpoint Ollama — [dev.to](https://dev.to/kasir-barati/does-pydantic-ais-structured-output-api-actually-work-against-ollamas-openai-compatible-endpoint-44aa)
- **Вторичные сравнения (вендорские или анекдотичные, верить с осторожностью).** Для «в основном линейных агентов, которые вызывают несколько инструментов и возвращают структурированный вывод» PydanticAI быстрее в разработке и проще в поддержке, чем LangGraph — [ZenML](https://zenml.io/blog/pydantic-ai-vs-langgraph). LangGraph 1.x — граф-рантайм с явными state machine, checkpointing, time-travel debugging и HITL interrupts — [Insoftex](https://insoftex.com/ai-agent-frameworks-2026-langchain-vs-langgraph/). LangGraph, CrewAI, PydanticAI и другие провайдер-агностичны, и разница между ними прежде всего в форме workflow — [FutureAGI](https://futureagi.com/blog/agentic-ai-frameworks-2025/)

### Inferences
- **Главное архитектурное решение: «LLM планирует, код исполняет».** Самая переносимая схема между провайдерами из РФ такая: LLM возвращает **JSON-план** (structured output, без нативного function-calling), а детерминированный исполнитель прогоняет инструменты из реестра. Причина в том, что у Yandex OpenAI-совместимый Chat Completions поддерживает только `temperature, max_tokens, stream, response_format`, а tools в OpenAI-режиме заявлены только для Responses API (см. раздел 7). Свободный ReAct-цикл с tool-calls можно оставить опциональным режимом «исследовать» для провайдеров, у которых tools работают.
- **Рекомендация по фреймворку:**
  1. **Основной вариант: PydanticAI 2.61 как слой «типизированный вызов LLM» плюс собственный оркестратор.** PydanticAI берёт на себя валидацию и ретраи по схеме, а также переключение `NativeOutput` → `PromptedOutput` для провайдеров без json_schema. Оркестратор (около 300 строк Python) отвечает за состояние, трейсы в БД и детерминированный fallback. **[общие знания]** У PydanticAI есть `TestModel`/`FunctionModel` для офлайн-тестов и инструментирование через Logfire/OpenTelemetry. Это стоит проверить в доках.
  2. **Альтернатива A: голый `openai` 3.x и Pydantic** с `response_format` или промптом со схемой, валидацией и одной попыткой repair. Минимум зависимостей и полный контроль. Подходит, если команда не хочет учить новый API.
  3. **Альтернатива B: OpenAI Agents SDK 0.24.** Выбирать, если провайдер поддерживает Responses API (Yandex заявляет полную поддержку) или если включён `set_default_openai_api("chat_completions")`. Обязательно вызвать `set_tracing_disabled(True)` или `set_trace_processors([DbTraceProcessor()])`. Собственный `TracingProcessor`, который пишет спаны в Postgres, — готовый источник для таймлайна в UI.
  4. **Альтернатива C: LangGraph 1.2.** Брать, если нужен честный durable HITL: граф ждёт ответа отельера через `interrupt` и checkpoint. За 2,5 дня такой граф дороже в отладке, а то же ожидание делается таблицей `questions` со статусом `pending`.
  5. **Не рекомендуется:** smolagents `CodeAgent`, который исполняет сгенерированный LLM Python. Это противоречит тезису кейса «LLM не угадывает», и ему нужен sandbox. CrewAI добавляет слой ролевых абстракций и усложняет контроль и трейсинг.
- **«Мультиагентность» лучше показывать как роли с типизированными входами и выходами, а не как чат агентов:** Planner/Collector, Verifier/Resolver, Interviewer (диалог с отельером), Search agent, Spec Compiler. В UI это отдельные «агенты» с собственными шагами в трейсе.
- **MCP.** Внутренний реестр инструментов достаточно сделать набором Python-функций с Pydantic-схемами параметров. **[общие знания]** FastMCP умеет монтироваться в ASGI-приложение, тогда реестр можно открыть как MCP-сервер по Streamable HTTP на `/mcp` в том же контейнере. Это дешёвый «бонус расширяемости»: в демо внешний агент (например, Claude Desktop) вызывает `compute_view`. Делать это стоит только после MVP. Внутренний агент должен вызывать функции напрямую, без сетевого хопа.

### Gaps
- Свежих независимых бенчмарков надёжности фреймворков с российскими провайдерами (Yandex, GigaChat) не нашёл. Совместимость PydanticAI с endpoint'ами Yandex и GigaChat надо проверить smoke-тестом в первый же час.
- Точный API `TracingProcessor` (`on_trace_start`, `on_span_end` и т. д.) на странице tracing не описан, нужно смотреть исходники `agents/tracing/processor_interface.py`.
- Включена ли у CrewAI по умолчанию телеметрия в 2026 году, не проверял.

## 2. Расширяемость: «характеристика как текст» → план над реестром детерминированных инструментов

### Takeaway
Характеристика описывается **декларативной спецификацией** (YAML или JSON плюс Markdown-описание). LLM-«компилятор» превращает свободный текст в такую спецификацию, ограничиваясь **белым списком инструментов** реестра. Затем идут статическая валидация, dry-run на 3 отелях, подтверждение человеком, версионирование и фоновый backfill. LLM никогда не генерирует исполняемый код или сырой Overpass QL. Он только выбирает инструменты и их параметры по JSON-схемам. Всё это хорошо ложится на форму «Добавить характеристику» в UI.

### Cited Findings
- Публичный Overpass API рассчитан примерно на <10 000 запросов в сутки и <1 ГБ в сутки. Для регулярного использования вики советует делить эти цифры на 100. Лимит считается на приложение, а не на пользователя. Параллельные скрипты запрещены. После 429/406 нужна пауза 30 с. Коммерческим пользователям нужен свой сервер — [OSM Wiki: Overpass API](https://wiki.openstreetmap.org/wiki/Overpass_API), [Overpass API User's Manual](https://dev.overpass-api.de/overpass-doc/en/preface/commons.html)
- По Instacart и DoorDash видно, что LLM в поиске работает на уровне понимания запроса и обогащения графа знаний, а сопоставление идёт с **каноническими атрибутами**. У DoorDash «no-milk» превращается в «dairy-free» — [ByteByteGo](https://blog.bytebytego.com/p/why-doordash-instacart-and-uber-eats). Тот же принцип годится для спецификаций: синонимы в спецификации ведут к каноническому `characteristic_id`.

### Inferences
- **Формат спецификации** (Pydantic-модель `CharacteristicSpec`, хранится как JSONB с версиями):
  ```yaml
  id: night_pharmacy_walk
  version: 1
  name_ru: "Круглосуточная аптека в 10 минутах пешком"
  description: "Есть ли круглосуточная аптека в пешей доступности ≤ 10 мин"
  synonyms: ["аптека ночью", "24/7 аптека", "ночная аптека рядом"]
  scope: hotel                    # hotel | building | facade | floor | room_type
  value_schema:                   # JSON Schema значения
    type: object
    properties:
      exists: {type: boolean}
      walk_min: {type: number, unit: min}
      nearest_osm_id: {type: string}
  methods:                        # что агенту РАЗРЕШЕНО использовать, с априорной надёжностью
    - tool: poi_nearby
      params: {tags: [{key: amenity, op: "=", value: pharmacy}], radius_m: 1200,
               opening_hours: "24/7"}
      prior_reliability: 0.75     # OSM opening_hours неполны
    - tool: walk_route
      params: {to: "$prev.nearest", profile: foot}
    - tool: ask_hotelier
      when: "confidence < 0.6"
      question: "Есть ли рядом круглосуточная аптека? Сколько идти пешком?"
  combine: "exists = walk_min <= 10"   # безопасный DSL-выражение (whitelist AST)
  ttl_days: 90
  change_triggers: [{osm_tags: ["amenity=pharmacy"], radius_m: 1200}]
  search:
    kind: boolean_soft            # как матчить в поиске
    explain_ok: "Круглосуточная аптека в {walk_min} мин пешком"
    explain_bad: "Ближайшая круглосуточная аптека дальше 10 мин"
  hotelier_answerable: true
  ```
- **Реестр инструментов: обобщённые примитивы**, из которых собирается большинство характеристик:
  - `poi_nearby(tags, radius_m, opening_hours?)` — локальная таблица OSM POI в PostGIS (`ST_DWithin` по geography). Возвращает количество, ближайший объект, расстояние и OSM id как evidence.
  - `walk_route(to, profile)` — предрасчитанные кратчайшие пути по пешеходному графу до типовых целей (пляж, метро, центр). Для новых целей используется fallback «прямая × коэффициент извилистости» с **меньшей уверенностью**. Это хорошая демонстрация того, что уверенность зависит от метода.
  - `noise_by_facade(side)` — дороги по классам, ж/д, бары и клубы с затуханием по расстоянию и экранированию зданиями.
  - `viewshed(target|direction, facade, floor)` — по предрасчитанной сетке высот (DEM + здания), см. раздел 8.
  - `sun_window(facade_azimuth, months)` — азимут заката по дате и пересечение с открытым сектором обзора.
  - `climate(month)` — кэш Open-Meteo.
  - `wikidata_building(hotel)` — год постройки, стиль, статус памятника.
  - `text_extract(source, question, schema)` — извлечение через LLM из описания или отзывов с **обязательной цитатой**. Низкий prior.
  - `ask_hotelier(question, schema)`.
  - `derive(expr)` — безопасный вычислитель выражений над другими характеристиками.
- **Компиляция текста в спецификацию.** На вход LLM подаются текст пользователя, каталог инструментов (имя, описание, JSON-схема параметров, стоимость, типичная надёжность) и примеры 2–3 готовых спецификаций. На выходе `CharacteristicSpec` (structured output). Затем идёт валидация:
  1. Инструменты есть в реестре, а параметры проходят их Pydantic-схемы.
  2. `value_schema` — валидная JSON Schema.
  3. OSM-теги из whitelist (или хотя бы `^[a-z_:]+$`), радиусы и таймауты в допустимых пределах.
  4. Выражение `combine` разбирается whitelisted-AST.
  5. Dry-run на 3 отелях с показом evidence.
  6. Человек подтверждает.
  7. Сохраняется `characteristic_versions(v)` и ставится backfill-задача.
  8. Характеристика автоматически попадает в каталог парсера запросов (синонимы плюс описание) и в фильтры UI.
- **Безопасность.** Сырой Overpass QL от LLM не принимается. Запрос строится кодом из структурированного фильтра. В рантайме инструменты ходят в **локальные таблицы** (предзагруженный OSM-экстракт региона), а не в живой Overpass. Живой Overpass остаётся только кнопкой «обновить из OSM» с троттлингом. Так соблюдаются лимиты, и демо работает офлайн.
- **Кэширование.** `tool_cache` с ключом `sha256(tool_id, tool_version, params, hotel_geom_version, data_snapshot_id)`. `llm_cache` с ключом `sha256(model, messages, schema)`. Второй кэш одновременно служит механизмом офлайн-демо (раздел 7).
- **UI «Добавить характеристику»:**
  1. Textarea «Опишите характеристику своими словами».
  2. Кнопка «Скомпилировать». Показываются YAML-спецификация в редакторе, план «какие инструменты и почему» и предупреждения валидатора.
  3. «Проверить на 3 отелях»: карточки со значениями, уверенностью, evidence и картой найденных POI.
  4. «Сохранить и посчитать для всех» с прогрессом backfill.
  5. Новая характеристика сразу находится через поиск, например «ночная аптека рядом».
  Это прямое и наглядное покрытие задачи 4.
- **Как честно показать задачу 1 («агент сам решает»).** Planner получает спецификацию и **контекст отеля**: покрытие высот зданий в радиусе 500 м (например, 40 %), наличие сайта и Wikidata, наличие ответа отельера. Он возвращает упорядоченный план с `rationale` и правилами остановки, например «если viewshed confidence < 0.6 → ask_hotelier». Детерминированный fallback сортирует `methods` по `prior_reliability / cost`. В трейсе видно, какие инструменты выбраны, какие отброшены и почему.

### Gaps
- Готовых open-source реализаций «spec → plan над реестром геоинструментов» именно для POI и геоаналитики не искал. Шаблон собран из общих практик structured output.
- Безопасный вычислитель выражений: подойдёт `simpleeval` или собственный AST-whitelist. Актуальную версию `simpleeval` не проверял.

## 3. Модель происхождения и достоверности: claims/evidence, PROV, калибровка, конфликты, свежесть

### Takeaway
Хранить нужно **не значения, а утверждения (claims)** с полным происхождением, а «факт» вычислять как результат разрешения конфликтов над claims. Разрешение конфликтов делается взвешенным голосованием по надёжности источников в духе truth discovery: итеративная оценка надёжности источника и истины. Учитываются **scope** (fasade/floor/room) и **свежесть**. Если победитель не очевиден или мнение отельера противоречит вычислению, генерируется уточняющий вопрос. Свежесть задаётся TTL на уровне спецификации и событиями изменений OSM. Для демо нужна заготовленная «новая постройка», после которой пересчитывается вид.

### Cited Findings
- **Общий принцип truth discovery.** «If a source provides trustworthy information frequently, it will be assigned a high reliability; meanwhile, if one piece of information is supported by sources with high reliabilities, it will have big chance to be selected as truth». Мажоритарное голосование ошибается, потому что считает все источники одинаково надёжными. Truth discovery умеет выбирать **миноритарное значение** от надёжного источника — [Li et al., A Survey on Truth Discovery (arXiv:1505.02463)](https://arxiv.org/abs/1505.02463)
- **Три семейства методов** — [Li et al., 2015](https://arxiv.org/abs/1505.02463):
  - итеративные: Investment, `vote(v) = (Σ_{s∈S_v} w_s/|V_s|)^1.2`, с обратным пересчётом весов источников;
  - оптимизационные: `argmin Σ_o Σ_s w_s·d(v_o^s, v_o*)`, где d — 0-1 loss для категориальных данных и L2 для непрерывных, решается coordinate descent;
  - вероятностные графические модели, например гауссова: истина — среднее, вес источника — точность (precision), вывод через EM.
  Общий алгоритм: инициализировать веса, затем повторять «вычислить истины при текущих весах → обновить веса» до сходимости.
- **Практические аспекты из того же обзора** — [Li et al., 2015](https://arxiv.org/abs/1505.02463):
  - для дубликатов от одного источника можно учитывать **свежесть** и брать последнее наблюдение;
  - при извлечении из текста стоит учитывать **неопределённость входа** (confidence экстрактора);
  - нужна **детекция копирования** между источниками, потому что зависимые источники завышают голоса;
  - для потоковых данных существуют отдельные алгоритмы;
  - даже **небольшой набор размеченных истин** улучшает оценку надёжности (semi-supervised).
- Overpass поддерживает augmented diffs (`adiff`) между двумя датами. Они показывают, что произошло с изменёнными и удалёнными объектами (до и после). Нужны `datetime` двух моментов, и фильтрацию по типу объектов надо делать самостоятельно — [osmdata: opq (adiff)](https://docs.ropensci.org/osmdata/reference/opq.html). Есть визуализатор изменений по области Achavi — [Achavi](https://overpass-api.de/achavi)

### Inferences
- **Схема claim** (таблица `claims`, append-only):
  `id, hotel_id, characteristic_id, spec_version, scope_type (hotel|building|facade|floor|room_type), scope_ref (jsonb: {"facade":"W","floors":[5,12]} | {"room_type":"Deluxe Sea"}), value (jsonb), value_num, value_bool, unit, source_id, method (tool_id@version), evidence (jsonb: osm_ids, query params, distances, geometry ref, цитата+offsets, message_id ответа отельера, snapshot ids), raw_confidence, confidence (калиброванная), observed_at (момент, к которому относятся данные: дата OSM-снапшота / ответ отельера), retrieved_at, valid_until, run_id (→ agent_runs), status (active|superseded|rejected), superseded_by`.
- **Факт** (`facts`, материализованное представление «текущей истины»): `hotel_id, characteristic_id, scope, value, confidence, status (confirmed|computed|disputed|unknown|stale), resolution (single|weighted_vote|hotelier_override|scope_split), supporting_claim_ids[], conflicting_claim_ids[], updated_at, valid_until`.
- **Отображение на W3C PROV [общие знания, PROV-O: https://www.w3.org/TR/prov-o/]:**
  - claim — `prov:Entity`;
  - запуск инструмента — `prov:Activity`, который `prov:used` OSM-снапшот, DEM и прочие сущности;
  - `prov:wasAssociatedWith` — агент («geo-collector v1», модель LLM или конкретный отельер);
  - claim `prov:wasGeneratedBy` активность;
  - fact `prov:wasDerivedFrom` claims;
  - `prov:generatedAtTime` соответствует `observed_at`, `prov:invalidatedAtTime` — `valid_until`/superseded.
  Полный RDF не нужен, достаточно, чтобы в UI была цепочка «значение ← claim ← запуск инструмента ← входные данные (снапшот OSM от даты X)». Это сильный аргумент для жюри.
- **Модель уверенности:**
  `confidence = prior(source, method, characteristic_family) × quality(method, context) × freshness(age)`.
  - `prior`: Beta-апостериор надёжности источника, `(correct+α)/(n+α+β)`. Стартовые α и β задаются вручную (OSM opening_hours ≈ 0.7, вычисленный viewshed при полном покрытии высот ≈ 0.85, отельер по внутренним фактам ≈ 0.9, LLM-извлечение без цитаты ≈ 0.4) и уточняются на размеченной выборке.
  - `quality`: доля зданий с известной высотой в секторе обзора, расстояние, разрешение DEM, наличие точной цитаты.
  - `freshness`: `exp(-ln2·age/half_life)` или ступенька после TTL.
  - **Калибровка:** на размеченной выборке строятся reliability diagram и Brier/ECE, затем делается isotonic или биннинг по семейству источников **[общие знания: sklearn.calibration]**. При 300–500 метках можно калибровать только по 3–5 крупным группам.
- **Детекция конфликтов** (для пары claims одной характеристики):
  - категориальные значения различаются;
  - числовые: `|a−b| > tol` (абсолютный или относительный допуск из спецификации);
  - **scope-aware**: «вид на море: да» (hotel) против «нет» (facade E) — это **уточнение**, а не конфликт. Факт разбивается по scope: `scope_split`;
  - **temporal**: новый claim того же источника и метода замещает старый (`superseded`) без конфликта.
- **Разрешение конфликтов:**
  1. `score(v) = Σ_{claims→v} w_source × confidence × freshness`.
  2. Если `margin = (top1 − top2)/Σ > 0.3` и `top1_conf > 0.6`, то `auto_resolved`.
  3. Иначе `disputed`. Конфликт попадает в очередь, а Interviewer формирует вопрос с evidence.
  4. **Политика по классу характеристики:** для «внутренних» фактов (шторы blackout, шумоизоляция, питомцы) отельер авторитетен (`hotelier_override`). Для внешне проверяемых (вид, расстояния, шум улицы) отельер не перебивает вычисление автоматически. Ему задаётся вопрос с доказательством, например: «По нашим данным, на запад перед отелем стоит 9-этажное здание (OSM way/123). Из каких номеров виден закат?». Ответ обычно превращает конфликт в `scope_split`, например «закат только с 7-го этажа».
  5. Итеративный truth discovery (Algorithm 1 из обзора) запускается пакетно по всем отелям региона и пересчитывает веса источников. В UI это таблица «надёжность источников». Детекция копирования важна: например, описание отеля на агрегаторе и ответ того же отельера — зависимые источники.
  6. **[общие знания]** Классический TruthFinder (Yin, Han, Yu, KDD 2007) итеративно пересчитывает trustworthiness источника и confidence факта с учётом сходства значений. Для хакатона достаточно взвешенного голосования с итеративным пересчётом весов.
- **Свежесть и TTL по типам** (значения по умолчанию, хранятся в спецификации):
  - рельеф и DEM — 5 лет;
  - здания и вид — 180 дней плюс пересчёт по событию OSM;
  - POI и часы работы — 60–90 дней;
  - стройки и мероприятия — 7–14 дней;
  - климатические нормы — 365 дней;
  - внутренняя политика от отельера — 180–365 дней;
  - цены и сборы от отельера (питомцы) — 90 дней.
- **Детекция изменений.** Хранить `osm_snapshot_ts`. Периодическая задача (а в демо кнопка) находит изменения в bbox региона: Overpass `adiff`/`newer:` или предзаготовленный fixture-diff. Фильтр: `building=*` создан или изменён, изменились `height`/`building:levels`. Пересечение с **радиусами влияния** характеристик (`change_triggers` в спецификации, например буфер viewshed 1–2 км в секторе обзора) даёт список затронутых (hotel, char). Им ставится `stale`, запускается recompute, а если значение изменилось, создаётся новый claim, старый помечается `superseded`, пишется событие в журнал изменений и уведомление в кабинет отельера.
- **Сценарий для демо:** в `data/fixtures/osm_change_new_tower.geojson` лежит 16-этажный дом напротив отеля X. Кнопка «применить изменение OSM» запускает пересчёт и показывает в UI, что «вид на море с 5–8 этажей пропал, остался с 9-го» с диффом evidence. Это прямое покрытие доп. задачи 4.

### Gaps
- Полного текста TruthFinder в этой сессии не открывал, формулы приведены по памяти и помечены.
- Готового рабочего примера Overpass QL «новые здания в bbox за период» не нашёл. Нужен эксперимент с `[adiff:"t1","t2"]` и фильтром `way["building"]`.
- Эмпирических значений надёжности OSM `opening_hours` и `height` для конкретного российского региона не искал. Это задача для собственной выборки.

## 4. Диалог с отельером: какой вопрос задать, как сформулировать, как разобрать ответ, симулятор

### Takeaway
Вопросы надо выбирать по упрощённой **ценности информации**: спрос на характеристику × неопределённость × «знает ли это отельер» / стоимость вопроса, с бюджетом в 3–5 вопросов на сессию. Подтверждение спорного значения с доказательством (да/нет плюс уточнение) задавать в первую очередь. Ответ разбирается через structured output по JSON-схеме, которая собирается из `value_schema` **всех открытых характеристик отеля**, с обязательной цитатой-основанием и Pydantic-валидацией. Отельер имитируется LLM со **скрытым профилем истины** и персоной, которая иногда даёт размытые или противоречивые ответы. Для офлайн-режима есть детерминированная шаблонная версия. Тот же профиль служит разметкой для метрик.

### Cited Findings
- Сам кейс требует: «Если данных нет или агент в них не уверен, он сам формулирует вопрос… Отельер отвечает в свободной форме, а агент раскладывает ответ по нужным полям», и разрешает имитировать отельера — [CASE.md](/Users/shttrkk/ostrovok-hack/materials/CASE.md)
- Режимы `NativeOutput` и `PromptedOutput` в PydanticAI позволяют получать типизированный разбор и у провайдеров без нативной JSON-схемы — [PydanticAI output API](https://pydantic.dev/docs/ai/api/pydantic-ai/output/)
- По OpenRouter structured outputs поддержка `json_schema`/`strict` зависит от endpoint. Часть провайдеров «конвертирует схему или считает её сильной подсказкой». Чтобы маршрутизировать только на поддерживающих провайдеров, нужен `provider.require_parameters: true` — [OpenRouter: Structured Outputs](https://openrouter.ai/docs/features/structured-outputs)

### Inferences
- **Приоритет вопроса (VOI-lite):**
  `priority(h,c) = demand(c) × uncertainty(h,c) × answerable(c) × (1 − computable_conf(h,c)) / cost(c)`
  - `demand(c)` — доля запросов в логе или в синтетическом наборе из 50–100 запросов, где упомянута характеристика c;
  - `uncertainty` — `1 − confidence`, энтропия, или 1 для `unknown`/`disputed`;
  - `answerable(c)` — флаг спецификации (отельер знает про шторы, но не про шум трассы ночью в децибелах);
  - `cost` — 1 для да/нет-подтверждения и 2–3 для открытого вопроса.
  Из этого строится жадный выбор top-k с группировкой связанных вопросов (питомцы: вид, вес, цена, площадка). Не спрашивать то, что вычислено с conf ≥ 0.8.
- **Формулировка.** Шаблон из спецификации плюс LLM-полировка. В вопрос входят контекст (что уже известно и откуда), варианты ответа («Да / Нет / Только часть номеров — какие?»), единицы и пример. Один вопрос в сообщении. Для спорных значений даётся evidence (раздел 3). Отельеру показываются кнопки быстрого ответа и поле свободного текста.
- **Разбор ответа:**
  1. Строится Pydantic-модель `HotelierAnswerParse` с полями `updates: list[FieldUpdate]`. В `FieldUpdate` входят `characteristic_id, scope, value (по value_schema), confidence_hint, quote (подстрока ответа)`, а также `unknown_fields`, `needs_clarification: str | None` и `contradicts_existing: list[characteristic_id]`.
  2. Схема собирается динамически, union по открытым характеристикам. Ответ «собак до 10 кг, 500 ₽/ночь, кошек тоже» должен разложиться на несколько полей сразу.
  3. Валидация: `quote in answer_text` (анти-галлюцинация), диапазоны (вес 0–100 кг), enum.
  4. Если валидация не прошла, делается одна repair-попытка, затем вопрос уточнения.
  5. Каждый update превращается в claim с `source=hotelier:<id>`, `evidence={message_id, quote}`, а после этого запускается разрешение конфликтов.
  6. Если ответ противоречит прошлому ответу того же отельера или вычислению, создаётся follow-up.
- **Детерминированный fallback-парсер** (без LLM): regex и словари для чисел и единиц («до 10 кг», «500 руб»), да/нет-маркеров («да», «есть», «конечно» / «нет», «к сожалению»), сторон света и этажей («с 5-го этажа», «западная сторона»). Покрывает кнопки быстрого ответа и демо-сценарии.
- **Симулятор отельера:**
  - `data/hotelier_profiles/<hotel_id>.yaml` содержит `truth` (значения характеристик со scope) и `persona`: `{style: лаконичный|многословный|путаный, p_vague: 0.2, p_wrong: 0.1, p_unknown: 0.15, lang: ru}`.
  - LLM-промпт: «Ты менеджер отеля X. Твои знания: <truth>. Отвечай в стиле <style>. С вероятностью p_vague отвечай уклончиво…». Случайность сидируется и решается **кодом**, а не LLM: какой вопрос получит размытый или ложный ответ, определяется заранее, что даёт воспроизводимость.
  - Офлайн-версия рендерит ответ из шаблонов по профилю и выбранному «искажению».
  - **[общие знания]** Похожий паттерн используется в τ-bench (Yao et al., 2024): пользователь симулируется LLM со скрытыми инструкциями.
- **Кабинет отельера.** Входящие вопросы, ответ свободным текстом или кнопками, таблица «что о вас знает система» с источником, датой и уверенностью для каждой строки, кнопки «подтвердить / исправить» (исправление даёт claim отельера и разрешение конфликта), журнал изменений.

### Gaps
- Публикаций именно про выбор вопросов отельеру (VOI для обогащения карточек) не искал. Формула выше — инженерная эвристика.
- Насколько хорошо YandexGPT, GigaChat и DeepSeek раскладывают русские свободные ответы в мульти-поле JSON, нужно проверить на 20–30 тестовых ответах.

## 5. Поиск на естественном языке

### Takeaway
Используется схема «LLM понимает запрос, классика ищет и ранжирует». LLM разбирает запрос в **жёсткие ограничения и мягкие предпочтения с весами** по **каталогу характеристик** (он формируется из спецификаций, поэтому новые характеристики сразу попадают в поиск). Затем идут SQL/PostGIS-фильтр, **ранжирование с учётом уверенности** (ожидаемая полезность с априорными долями для неизвестных значений) и **шаблонные объяснения** по каждому критерию (✓ / ~ / ✗ / ?) со ссылкой на evidence. Векторный поиск (pgvector) нужен только для «остатка» запроса и свободного текста. При сотнях отелей скоринг выполняется в памяти за десятки миллисекунд. Узкое место по латентности — один LLM-вызов, поэтому его кэшируют и показывают пользователю чипы распознанных условий.

### Cited Findings
- Instacart перешёл от нескольких ML-моделей к единой LLM-системе понимания запроса: RAG для контекста, пост-guardrails, дообученная Llama-3-8B. Покрытие query rewrite выросло до >95 %. Semantic Role Labeling извлекает продукт, бренд и атрибуты, которые питают retrieval, ranking и фильтры — [Instacart Tech Blog](https://tech.instacart.com/building-the-intent-engine-how-instacart-is-revamping-query-understanding-with-llms-3ac8051ae7ac), [ZenML LLMOps DB summary](https://www.zenml.io/llmops-database/revamping-query-understanding-with-llms-in-e-commerce-search)
- В таких системах LLM живёт на уровне понимания запроса, а retrieval и ranking остаются классическими ML/IR. У DoorDash атрибут из запроса нормализуется к каноническому значению («no-milk» → «dairy-free») — [ByteByteGo](https://blog.bytebytego.com/p/why-doordash-instacart-and-uber-eats)
- **pgvector 0.8.7.** HNSW создаётся как `CREATE INDEX ... USING hnsw (embedding vector_cosine_ops)`, оператор `<=>` — косинусное расстояние. Фильтры у приближённых индексов применяются **после** скана индекса, поэтому при селективных фильтрах результатов может быть мало: при 10 % совпадений и `ef_search=40` в среднем около 4 строк. Решение — `SET hnsw.iterative_scan = strict_order | relaxed_order` с лимитом `hnsw.max_scan_tuples` (по умолчанию 20 000) — [pgvector README](https://github.com/pgvector/pgvector)

### Inferences
- **Схема разбора запроса** (`ParsedQuery`, structured output):
  ```json
  {"hard": [{"char": "sea_distance_walk_m", "op": "<=", "value": 800}],
   "soft": [{"char": "quiet_night", "target": true, "weight": 0.9},
            {"char": "sunset_view", "target": true, "weight": 0.7, "scope_pref": {"min_floor": null}}],
   "context": {"month": 7, "party": {"kids": 0, "pet": null}},
   "geo": {"anchor": null},
   "residual_text": "",
   "unmapped": ["атмосферный"]}
  ```
  В промпт передаются каталог характеристик (id, синонимы, тип значения, единицы) и правила: «недалеко» превращается в soft с порогом из спецификации, «обязательно» и «только» — в hard. Fallback без LLM: лемматизация (**[общие знания]** `pymorphy3`), сопоставление с синонимами спецификаций через `rapidfuzz` 3.14 и regex для чисел, расстояний и месяцев. Плюс кэш разборов для демо-запросов.
- **Кандидаты:**
  1. Регион или bbox через PostGIS.
  2. Hard-ограничения. Отель исключается, только если он **известно не подходит** с conf ≥ 0.7. Отели с `unknown` остаются с пометкой «не подтверждено» и штрафом.
  3. При желании top-N по `residual_text` через pgvector или Postgres full-text (`to_tsvector('russian', ...)`) как fallback без эмбеддингов.
- **Скоринг с учётом уверенности** (на каждый soft-критерий i):
  - `m_i ∈ [0,1]` — функция соответствия из спецификации. Для boolean это 1/0, для числовых — сигмоида вокруг порога, для scope-ограничений частичное соответствие: закат только с 5-го этажа даёт 0.7 и примечание.
  - `c_i` — уверенность факта, `p_i` — априорная доля «да» в регионе для неизвестных значений.
  - `S = Σ w_i·(c_i·m_i + (1−c_i)·p_i) / Σ w_i − λ·Σ w_i·(1−c_i)/Σ w_i` (λ ≈ 0.1 — штраф за неопределённость, risk-averse).
  - Tie-break по близости векторов и рейтингу.
  - **[общие знания]** Если ранжировщиков несколько (структурный и векторный), их удобно сливать через Reciprocal Rank Fusion (`1/(60+rank)`, Cormack et al., SIGIR 2009).
- **Объяснения.** Сначала детерминированные шаблоны из спецификаций (`explain_ok`/`explain_bad`) с подстановкой значений, источника, даты и уверенности: «✓ До пляжа 420 м пешком (6 мин), без пересечения трассы — OSM, 12.10.2026, 0.9»; «~ Закат виден только с 5-го этажа (западный фасад) — расчёт видимости, 0.8»; «? Шумоизоляция не подтверждена — спросили отельера». Опционально LLM сглаживает текст. Ему передаются только эти строки и ID фактов, и проверяется, что числа в выходном тексте совпадают с фактами. Так задача «Объяснение выбора» закрывается без галлюцинаций.
- **Unknown-значения.** Отдельный бейдж «нет данных», учёт через `p_i` в скоринге и кнопка «спросить отельера» (ставит вопрос в очередь Interviewer). Это замыкает цикл «поиск → спрос → вопросы».
- **Бюджет латентности** (≤1000 отелей):
  - LLM-разбор 1–3 с (из кэша — около 0);
  - SQL меньше 50 мс;
  - скоринг в Python/numpy меньше 50 мс: все факты региона можно держать в памяти, это ≤1000 × ~30 значений;
  - шаблонные объяснения — около 0.
  UX: сначала стримить или показывать чипы распознанных условий, пользователь может их редактировать (прозрачность и исправление ошибок парсера), потом список и карту.
- **Сравнение отелей** (доп. задача 2). Таблица характеристик × 2–4 отелей с цветом по match и иконкой уверенности. Данные те же, что для объяснений.

### Gaps
- Публичных разборов LLM-понимания запросов именно в travel-поиске (Booking, Airbnb, Островок) не нашёл. Поиск по Airbnb ничего не дал.
- Оптимальные веса и λ подбираются на собственном наборе размеченных запросов, внешних ориентиров нет.

## 6. Оценка качества: размеченная выборка и метрики

### Takeaway
Для 2,5 дней реалистична выборка из **30–50 отелей × 8–12 характеристик (≈300–500 меток)** с ручной проверкой (фото, панорамы, сайты) и стратификацией по сложным случаям. Плюс **15–25 размеченных запросов** с графической релевантностью top-10. Метрики:
- accuracy, P/R/F1 по характеристикам и MAE для числовых;
- покрытие и кривая risk–coverage по порогу уверенности;
- калибровка (Brier, ECE, reliability diagram);
- доля вопросов к отельеру и точность разбора ответов;
- nDCG@5/10 и constraint satisfaction rate для поиска.
LLM-as-judge подходит только как вспомогательный инструмент для оценки «верности» объяснений, с ручной сверкой.

### Cited Findings
- Кейс прямо называет метрики: «точность характеристик, покрытие, доля вопросов к отельеру» на собственной размеченной выборке — [CASE.md](/Users/shttrkk/ostrovok-hack/materials/CASE.md)
- Даже небольшой набор размеченных истин улучшает оценку надёжности источников в truth discovery (semi-supervised) — [Li et al., 2015](https://arxiv.org/abs/1505.02463)

### Inferences
- **Дизайн выборки.** 40 отелей одного региона, стратифицированных по типу локации: первая линия, второй ряд за высотками, центр, у ж/д или трассы, тихие районы. На каждый 10 характеристик: 4 геовычисляемые (вид на море с этажа, закат, шум ночью, пешком до пляжа), 2 по OSM POI (ночная аптека, детская площадка), 1 из Wikidata, 3 «отельерские» (питомцы, шторы, шумоизоляция; истина из профиля симулятора). Разметка: Яндекс/Google-панорамы и фото отзывов для вида; пешие маршруты — ручной замер в картографическом сервисе; часы работы — сайты. На 20 % выборки желательна двойная разметка для оценки согласия, **[общие знания]** Cohen's κ.
- **Метрики характеристик:**
  - бинарные: accuracy, precision/recall/F1 по классу «да»;
  - числовые: MAE и доля в допуске (±100 м, ±2 мин);
  - со scope: точность min_floor ±1 этаж и точность фасада;
  - **покрытие** — доля пар (отель, характеристика) с non-unknown значением при conf ≥ τ;
  - **selective accuracy / risk–coverage**: accuracy только по фактам с conf ≥ τ при τ ∈ {0.5, 0.6, …, 0.9}. Это показывает, что уверенность «работает»;
  - **калибровка**: Brier score и ECE (5 бинов), reliability diagram **[общие знания]**;
  - **доля вопросов к отельеру** — вопросов на пару (отель, характеристика) и доля характеристик, закрытых только отельером;
  - точность разбора ответов отельера: field-level exact match на 50–100 сгенерированных ответах, отдельно для размытых и противоречивых персон;
  - детекция конфликтов: precision/recall на искусственно внесённых противоречиях;
  - реакция на изменения: на fixture «новый дом» все затронутые факты должны стать stale и пересчитаться.
- **Метрики поиска.** 20 запросов разной сложности, например «тихий номер с видом на закат недалеко от моря», «с собакой до 15 кг и площадкой для выгула», «с детьми, пляж без перехода трассы». Pooling top-10 от системы и baseline (только звёзды и расстояние) с оценкой 0/1/2. Считаются nDCG@5/10, P@5, **constraint satisfaction rate** (доля top-5, реально удовлетворяющих hard-условиям по ground truth), качество разбора запроса (F1 по извлечённым условиям против эталонной разметки) и латентность p50/p95.
- **Подводные камни LLM-as-judge [общие знания: Zheng et al., 2023, «Judging LLM-as-a-Judge», arXiv:2306.05685]:** позиционная предвзятость, предпочтение длинных ответов (verbosity) и self-enhancement (модель завышает оценку своим ответам). Поэтому:
  1. для фактической верности объяснений используются детерминированные проверки (числа и значения в тексте совпадают с фактами в БД);
  2. LLM-судья используется только для «понятности и полноты» с рубрикой, перестановкой порядка и сверкой 20 % вручную;
  3. судья не должен быть той же моделью, что генерирует.
- **Подача.** `make eval` → `data/eval/results.json` (коммитится) → страница `/metrics` в UI: таблица по характеристикам, risk–coverage, reliability diagram, «доля вопросов», nDCG. Дата прогона и версия кода указываются явно.

### Gaps
- Нормативов «сколько меток достаточно» для такого прототипа нет. Цифры выше — компромисс по времени.
- Источника по Brier/ECE и κ в этой сессии не открывал (помечено как общие знания).

## 7. LLM-провайдеры с OpenAI-совместимым API, доступные из РФ (2026), и graceful fallback

### Takeaway
Основной провайдер для команды из РФ — **Yandex AI Studio**: рубли, юридически чисто, OpenAI-совместимый API. Но Chat Completions там совместим **частично** (`temperature, max_tokens, stream, response_format`), а tools заявлены через Responses API. Альтернативы:
- **GigaChat** через прокси `gpt2giga`: частичная совместимость, токен на 30 минут, самоподписанные сертификаты;
- **DeepSeek** напрямую: дёшево, модели V4.x;
- **OpenRouter**: один ключ на всё, но оплата из РФ затруднена;
- **Ollama** локально: tools и JSON mode, но у жюри может не быть ресурсов.
Архитектура не должна зависеть от провайдера: нужен адаптер с флагами возможностей и **полностью рабочий режим без ключа** (детерминированные парсеры плюс кэш LLM-ответов в репо).

Порядок structured output: native json_schema, потом json_object с Pydantic-валидацией, потом prompted, потом repair (1 ретрай).
- **Режим без ключа (`LLM_PROVIDER=none` или пустой `LLM_API_KEY`) — обязателен.** Жюри может запустить без ключа, и тогда:
  1. `llm_cache` засеивается из `data/llm_cache.jsonl`, где лежат все LLM-ответы демо-сценариев: 10–20 демо-запросов, 2–3 диалога с отельером, 1–2 компиляции характеристик. Ключ кэша — хэш промпта, поэтому демо-сценарии воспроизводятся байт-в-байт.
  2. Для новых запросов работают детерминированные компоненты: rule-based парсер запроса (синонимы спецификаций и regex), шаблонные вопросы, regex-парсер ответов, симулятор отельера на шаблонах, компилятор характеристики в режиме «только YAML» (форма принимает YAML-спецификацию без свободного текста).
  3. В UI бейдж «LLM: офлайн (кэш)», `/health` остаётся `ok`, а отдельный `/api/status` показывает режим.
- **Эмбеддинги.** Эмбеддинги отелей и характеристик предрасчитываются один раз и коммитятся. Это мало: 500 × 768 float32 ≈ 1,5 МБ. Эмбеддинг запроса берётся по API, если ключ есть (у Yandex есть Embeddings API). Иначе векторная стадия пропускается и работает Postgres full-text (`russian`). Локальную модель `fastembed` 0.9.1 скачивать на старте не стоит: сеть плюс сотни МБ ставят под угрозу лимит в ≤10 минут.

## 8. Развёртываемый стек: БД, бэкенд, фронтенд, офлайн-карты, Docker

### Takeaway
- **PostgreSQL 17 + PostGIS 3.6 + pgvector 0.8.x** в одном контейнере: `FROM postgis/postgis:17-3.6` плюс `apt-get install postgresql-17-pgvector` из того же PGDG-репозитория.
- **FastAPI**, который сам раздаёт собранный **React + Vite + MapLibre** фронт (один app-контейнер на 8080, без Node в рантайме).
- **Protomaps PMTiles**-экстракт города в репо, раздаётся тем же FastAPI: Starlette поддерживает HTTP Range.
- Все тяжёлые гео-расчёты (DEM, viewshed, графы) делаются **офлайн** в `pipeline/`, а в рантайм-образ попадают только numpy, shapely и pyproj без GDAL.
- Сиды и миграции выполняются на старте за секунды.

### Inferences
- **БД, рекомендация.** Postgres+PostGIS+pgvector в контейнере `db`:
  ```dockerfile

  FROM postgis/postgis:17-3.6
  RUN apt-get update && apt-get install -y --no-install-recommends postgresql-17-pgvector \
  ```

- **Бэкенд.** FastAPI, Pydantic v2, SQLAlchemy 2.1 + GeoAlchemy2 (или чистый SQL через psycopg 3 — меньше магии), Alembic. Фоновые задачи (backfill, пересчёт, очереди вопросов) выполняются **in-process** через asyncio-воркер плюс таблицу `jobs`, без Redis и Celery: меньше сервисов и меньше рисков на старте. Она сохраняется как `.npy` или `.npz`: 10 м/пиксель на 10×10 км — 1 000 000 × float16 ≈ 2 МБ. ## 9. Наблюдаемость для демо: трейсы и таймлайн рассуждений агента в UI

### Takeaway
Трейсы стоит писать в **собственные таблицы** `agent_runs`/`agent_steps` в той же Postgres и показывать на странице «Как агент это узнал»: таймлайн шагов (план → вызовы инструментов → evidence на карте → разрешение конфликта → вопрос отельеру), с JSON входов и выходов, временем, cache hit и rationale планировщика. Внешние системы (Langfuse v3 требует ClickHouse, Redis и S3; Phoenix — отдельный контейнер) для сдачи не нужны. В них можно экспортировать опционально через OTel.

### Cited Findings
- OpenAI Agents SDK даёт API собственных процессоров (`add_trace_processor`, `set_trace_processors`) и типизированные спаны (agent, generation, function, guardrail, handoff, turn, custom) — [OpenAI Agents SDK: Tracing](https://openai.github.io/openai-agents-python/tracing/)
- Langfuse v3 self-host требует четырёх компонентов: Postgres, Redis, S3/MinIO и ClickHouse — [Langfuse self-hosting](https://langfuse.com/self-hosting)
- Актуальные версии опциональных инструментов: `arize-phoenix` 20.26.1, `langfuse` 5.0.4, `logfire` 5.3.0 — [PyPI arize-phoenix](https://pypi.org/project/arize-phoenix/), [PyPI langfuse](https://pypi.org/project/langfuse/), [PyPI logfire](https://pypi.org/project/logfire/)

### Inferences
- **Схема:**
  - `agent_runs(id, kind: collect|interview|search|compile_spec|refresh, hotel_id?, characteristic_id?, trigger: user|schedule|osm_change|backfill, status, started_at, finished_at, llm_mode: live|cache|offline, model, tokens_in, tokens_out, cost_estimate)`;
  - `agent_steps(id, run_id, parent_step_id, seq, agent: planner|collector|resolver|interviewer|search|compiler, type: plan|llm_call|tool_call|decision|conflict|question|answer_parse|claim_write, name, input jsonb, output jsonb, rationale text, evidence_refs jsonb, duration_ms, cache_hit bool, error)`.
- **Обёртки.** Декоратор `@traced_tool` на каждом инструменте реестра и единая обёртка вокруг `LLMClient`. Если взять OpenAI Agents SDK, нужен `DbTraceProcessor` через `set_trace_processors`. Если PydanticAI — OTel-инструментирование с собственным exporter в БД или просто ручные шаги в оркестраторе.
- **UI.**
  - Вертикальный таймлайн (shadcn Accordion) с иконками агентов. Клик по tool_call подсвечивает на карте найденные POI, линии видимости и маршрут: это geometry в `output.geojson`.
  - Бейдж «LLM / кэш / детерминированно» на каждом шаге.
  - Живое обновление через SSE `/api/runs/{id}/stream`.
  - Из карточки отеля по каждому факту ведёт ссылка «показать, как получено» на соответствующий run.
- **Честность rationale.** Поле `rationale` от LLM-планировщика — модельное объяснение, а не доказательство. В UI его стоит подписывать «обоснование агента», а доказательства (evidence) показывать отдельно.

**10.5. Риски и смягчения**

| Риск | Смягчение |
|---|---|
| У жюри нет ключа LLM или провайдер недоступен | Офлайн-режим по умолчанию в `.env.example`, `llm_cache.jsonl` для всех демо-сценариев, детерминированные парсеры, бейдж режима в UI; smoke-тест без ключа в CI/Makefile |
| Провайдер не поддерживает tools или json_schema (Yandex Completions, Ollama) | Планировщик через JSON-план, а не tool-calls; `LLM_STRUCTURED_MODE` с каскадом native → json → prompted → repair; smoke-тест каждого провайдера в первый час |
| Галлюцинации LLM («угадал вид на море») | LLM не выдаёт значения характеристик без evidence: только выбор инструментов, разбор текста с цитатой и формулировки; claims от `text_extract` получают низкий prior; объяснения на шаблонах |
| Сборка amd64 на Apple Silicon медленная или падает | Стадия фронта с `--platform=$BUILDPLATFORM`, в Python-стадиях только wheels (без компиляции), `requirements.lock` с хэшами, закреплённые базовые образы; прогон с `--no-cache` и замер времени |
| Объём данных в git (PMTiles, DEM) | Экстракт по bbox и maxzoom ≤15, DEM не коммитится (только итоговая DSM-сетка .npz на нужном разрешении), без LFS, контроль файлов >50 МБ |
| Лимиты и простои Overpass, сеть на старте | Никаких сетевых вызовов на старте; всё из seed; живой Overpass только по кнопке, с троттлингом и User-Agent |
| В OSM нет высот зданий → неверный viewshed | Fallback: `building:levels`×3 м, потом дефолт по типу здания; доля зданий с известной высотой → `quality` в confidence; при низком покрытии автоматически вопрос отельеру «с какого этажа виден …» |
| Разрешение DEM (30 м), деревья, остекление | Результат даётся диапазоном этажей с умеренной уверенностью (≤0.8); проверка на размеченной выборке; явные оговорки в объяснении |
| Компилятор характеристик даёт невалидный план | Белый список инструментов, Pydantic-валидация параметров, AST-whitelist для `combine`, dry-run с подтверждением человеком, в офлайне только YAML |
| Неустойчивый разбор свободных ответов отельера | Мульти-полевая схема с обязательной цитатой и проверкой `quote in text`, repair-ретрай, уточняющий вопрос, кнопки быстрого ответа; метрика точности на 50–100 синтетических ответах |
| Время старта > 10 мин | Seed через `COPY` из csv.gz (секунды), миграции идемпотентны, healthcheck `start_period`; нет скачивания моделей и данных при старте |
| Разрастание объёма (scope creep) | MVP-план по дням, заморозка фич 28.10 в 18:00, в последний вечер только полировка и видео |
| Путаница с портом и путями | Один app-контейнер на 8080, SPA и API (`/api/*`, `/health`) с одного origin, без CORS |
