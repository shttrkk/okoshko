## Поведение после изменений

- **Р7.** Известное `no` обязательного условия опускается ниже неразрешённого условия. При одинаковой полноте выполнения настоящий, свежий, непротиворечивый ответ отеля с цитатой получает приоритет перед demo confidence. Общая формула utility сохранена; demo-факты не удаляются. Правило одинаково действует для обычного и группового поиска.
- **Р8.** Причинная формулировка `why_higher` появляется у лидера, только если пересчёт этого отеля без чистого поддерживающего демо-ответа действительно лишает его первого места. Для обычного поиска сравниваются исходные ключи сортировки, до округления score; причина не зависит от размера страницы. Например: «Выше в выдаче из-за ответа отеля про тишину — это демо-ответ». Смешанный Fact с независимым расчётом или открытыми сведениями не удаляется ради такого вывода: для него показывается только проверяемый состав источников — «По условию «Тишина ночью» учтён ответ отеля · демо вместе с расчётом по карте». Неизвестное условие не становится причиной рекомендации. `relative_reason` больше не объясняет одинаковые статусы выдуманным «данные надёжнее» или голыми баллами. Разные условия одного CID сопоставляются по своей подписи.
- **Р9.** Наличие Wi-Fi по карте при неизвестной скорости остаётся `partial`, `condition_met=false`: «Wi-Fi есть по карте · скорость неизвестна». Желаемые 30 Мбит/с не попадают в текст результата как достигнутая скорость. Для явного запроса Wi-Fi агрегированные fixed/mobile тесты района не подтверждают сеть отеля. Поле желания и исходные наблюдения не изменяются.
- **Р11.** «В коляске», «с коляской» и готовый семейный пример добавляют обязательный `accessible_route`; прежнее ограничение `beach_walk` без лестниц сохраняется. Прокат, аренда, пересказ, вопрос о значении слов, отрицание и гипотетический сценарий не создают это требование автоматически. Реальный маршрут с лестницами даёт `no`. Без лестниц, при известных подъёме и переходах, он даёт только `partial` с непроверенными бордюрами, шириной и проездом у входов. При недостающих барьерах остаётся `unknown` с причиной. Полное выполнение по карте не заявляется. Собственное подтверждение доступности отелем не перекрывается маршрутным fallback.
- **Р13.** Обе дословные фразы Дины уже распознавали `location_access.in_central_sochi` в исходной версии. Добавлены проверки этого поведения. «В центре города» и «центральный район» теперь не оставляют лишних слов. «Ближе к центру» без измеримого порога явно остаётся в `unmapped` с объяснением; минуты не выдумываются. Если характеристики центра нет в каталоге, слово не игнорируется молча.
- **Т1.** Root-коммит исправляет fallback обычного имени «пляж», `beach` и OSM-кодов на «ближайший пляж». Поисковые проверки сохраняют исходный Fact и evidence без изменений.
- **Т3.** При запросе тишины реальный свежий бар ближе 100 м становится отдельным риском: «Рядом бар — ≈ 94 м по карте. Ночью может быть шумно; часы работы и слышимость в номере неизвестны». `context_fact_ids/context_evidence_refs` указывают на nightlife; основные `fact_ids/evidence_refs` по-прежнему доказывают только тишину. Статус и confidence тишины не подменяются сведениями о баре.
- **Т8.** «Спокойный номер», «спокойный район» и «тихий район» однозначно распознаются как тишина. Изменения словаря YAML выполняет поток hotelier.

Производная оценка доступности не создаёт выдуманный Fact, CID или идентификатор. Исходный `beach_walk` доступен только как контекст, его confidence сохраняет надёжность исходного маршрута; `condition_met=false` не допускает `all`. Известное самостоятельное препятствие `accessible_route` также не перекрывается маршрутом без лестниц.

Для поиска и пробного прогона используется общий root-helper `required_fulfilled`: все обязательные должны иметь поддержку, без domain/scope conflict. В режиме похожих отелей сохранены прежние ограничения для наблюдаемого поля, но отсутствие самого нужного поля, например скорости Wi-Fi, больше не скрывает все альтернативы после перехода характеристики в `awaiting_hotels`. Такие альтернативы сохраняют `unknown/partial` и честный счётчик обязательных условий.

## Интеграция и ограничения

- Зависимости: root `a80c25d` (контракт `why_higher`, generic beach fallback), `d60250c` (общая семантика выполнения обязательных). Оба получены обычным fast-forward merge. Реализация и этот отчёт входят в Conventional Commit `fix(search): ground panel ranking and route expectations` текущей ветки; точный hash передан root после коммита.
- Root должен добавить `nightlife` к выборке `repo.search_facts` вместе с `airport_noise` при запросе `quiet_night`; иначе оптимизированный HTTP поиск не загрузит бар для контекста. Изменение согласовано, API-файл не менялся этим потоком.
- Guest-потоку переданы: видимый `why_higher`, причины номера только по `verdict.status == yes` с явным demo, специальный Wi-Fi text без порога, сохранение backend-порядка для обязательного `no`, отдельные ссылки рисков. Гостевой слой должен убирать дБ/углы/методы в технические подробности; исходные данные остаются доступны в evidence.
- Отельер-потоку переданы точные YAML-правки quiet synonyms и описания accessible_route. Голые stroller synonyms не добавлялись, чтобы сохранить guarded intent.
- Живые записи Mercure, сохранённые 18 demo-check и браузерный прогон на :8081 проверяет root после объединения потоков. Этот поток не записывает в эти стенды. Unit fixtures не являются фактами об отелях.
- GET-only проверка :8081 установила, что quiet demo-факты Cascade `eef4b90ec7a47f2fbdd1fead8a461e32`, Brevis `b6ffabc7f4331cd7ae56b249385ecaa1` и Приморской `77097a69daa9f7e57d4de5f785ce6990` содержат одновременно simulation/hotelier_simulator quote и calculation OSM/Overture/DEM. У всех трёх также есть самостоятельный реальный facade calculation с `available=true`. Поэтому для этих смешанных фактов причинное «из-за demo» не заявляется; показывается состав источников.
- Без маршрута, измерения скорости, ответов отеля или данных о барьерах система не получает основания обещать их наличие. Картографический маршрут не проверяет бордюры, ширину, реальные входы и проезд на инвалидной коляске.
